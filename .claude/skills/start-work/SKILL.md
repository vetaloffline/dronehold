# /start-work — свіжий main і нова гілка під задачу

Вхід: `$ARGUMENTS` — опис задачі; з нього назва гілки.

Правила для всіх кроків:
- Кожна команда `git` і `gh` — окремим викликом Bash з кореня репо: без `cd … &&`, без `git -C`, без пайпів
  після `gh`. Інакше команда не потрапляє в `excludedCommands` sandbox і падає на мережі/TLS.
- Нічого не форсувати: без `--force`, `-D`, `reset --hard`.
- СТОП = вивести причину й вивід команди, що впала, чекліст з кроку 8 і завершити skill без подальших кроків.

## Крок 0. Довідка

`$ARGUMENTS` = `--help` або `-h` → вивести блок нижче дослівно і завершити skill (нічого не змінювати).

```
/start-work <задача>

Розбирається з незакоміченими змінами (перенести / стеш / коміт — питає), стягує свіжий main
і створює від нього гілку <тип>/<назва>. Змерджені гілки видаляє.

  <задача>     вільний текст; з нього тип гілки (feat, fix, art, docs, refactor, test)
               і назва з 2–4 англійських слів; порожньо — спитає
  -h, --help   ця довідка

Приклади:
  /start-work ремонтний дрон лагодить стіни   → feat/repair-drone
  /start-work виправ кут ствола кулемета      → fix/machine-gun-barrel-angle
```

Інакше → крок 1.

## Крок 1. Задача

`$ARGUMENTS` порожній → спитати «Яка задача?»; відповідь = задача. → крок 2.

## Крок 2. Зібрати стан

1. `git branch --show-current` → `BRANCH`.
2. `git status --short` → `DIRTY` = є хоч один рядок.
3. `git fetch origin --prune`. Помилка → СТОП.
4. `BRANCH` ≠ `main` → `gh pr view --json state` → `PR_STATE` = `OPEN` | `MERGED` | `CLOSED`; помилка
   «no pull requests found» → `PR_STATE` = `NONE`.

`DIRTY` = ні → крок 4. `DIRTY` = так → крок 3.

## Крок 3. Незакомічені зміни

Показати вивід `git status --short` і спитати через AskUserQuestion «Що зробити з цими змінами?».
Варіанти — тільки ті, що проходять умову:

| Варіант | Умова | Дія |
|---|---|---|
| Перенести в нову гілку | завжди | нічого; `git switch -c` у кроці 6 забере зміни з собою |
| Стеш | `BRANCH` ≠ `main` | `git stash push -u -m "<BRANCH>: before <задача>"` |
| Коміт | `BRANCH` ≠ `main` і `PR_STATE` ∈ {`OPEN`, `NONE`} | `git add` змінених файлів → `git commit` (заголовок англійською, у стилі `git log --oneline -10`, без підпису Claude) → `git push -u origin HEAD` |

`BRANCH` = `main` → у питанні додати: «На main хук guard-main.py блокує stash і commit, тому тільки перенос».
Помилка дії → СТОП. → крок 4.

## Крок 4. Свіжий main

- `BRANCH` = `main` → `git pull --ff-only`.
- Інакше → `git fetch origin main:main` (оновлює локальний main без переходу на нього).

Помилка (локальний main має свої коміти) → СТОП. → крок 5.

## Крок 5. Назва гілки

1. `<тип>/<назва>`. Тип з задачі: нова механіка чи об'єкт → `feat`; виправлення помилки → `fix`; тільки арт →
   `art`; доки, правила, skills → `docs`; перебудова коду без зміни поведінки → `refactor`; тільки тести → `test`.
2. Назва — 2–4 англійські слова через дефіс із задачі (`feat/relay-build-radius`, `art/slime-skins`).
3. `git rev-parse --verify --quiet refs/heads/<гілка>` успішний або `git ls-remote --heads origin <гілка>`
   непорожній → додати `-2`, `-3`… до вільної.

→ крок 6.

## Крок 6. Створити гілку

`git switch -c <гілка> main`. Помилка (зміни конфліктують зі свіжим main) → СТОП. → крок 7.

## Крок 7. Прибрати змерджені гілки

Тільки на новій гілці (на `main` хук блокує `git branch -d`).

1. `git branch --merged main` → список.
2. Для кожної гілки зі списку, крім `main` і нової: `git branch -d <гілка>`. Відмова git → записати для звіту,
   продовжити з наступною.

→ крок 8.

## Крок 8. Звіт людині

Вивести чекліст (`[x]` зроблено, `[ ]` не зроблено, `[–]` пропущено — з причиною):

```
- [x] Незакомічені зміни: перенесено / стеш `<повідомлення>` (повернути: `git stash pop`) / коміт `<хеш>`  |  [–] змін не було
- [x] Свіжий main: <git log -1 --oneline main>
- [x] Нова гілка: <гілка>
- [x] Змерджені гілки видалено: <список>; git не дав видалити: <список>  |  [–] нема змерджених
```

СТОП на будь-якому кроці → той самий чекліст: що встигли — `[x]`, на чому зупинились і решта — `[ ]`.
